🔒 Phase 2 — Attack Test Harness

Tests A–J against the OS auth gate. Each test proves a specific attack vector is blocked.

Attack A — Forged Token (modified payload, original signature) PASS — REJECTED
Attacker modifies the token payload (e.g., changes studentId or founder flag) but keeps the original signature. The signature no longer matches the modified payload.
→ OS calls verifyToken(modifiedToken)
→ System A /api/verify-token validates signature against payload
→ Signature mismatch → { valid: false, error: "invalid-signature" }
→ rfxAuthGate() returns false → TRUST = null, TRUST_VERIFIED = false
→ Ring shows: "— / Demo trader"
Attack B — Completely Fabricated Token (fake signing key) PASS — REJECTED
Attacker creates a token with a completely fabricated signing key. The token is structurally valid but cryptographically meaningless.
→ OS calls verifyToken(fabricatedToken)
→ System A /api/verify-token attempts signature verification
→ Verification fails → { valid: false, error: "invalid-signature" }
→ rfxAuthGate() returns false → no auth, no trust
Attack C — Expired Legitimate Token PASS — REJECTED
Attacker uses a previously valid token after its exp timestamp. The signature is valid but the token has expired.
→ OS calls verifyToken(expiredToken)
→ System A /api/verify-token checks exp claim
→ Token expired → { valid: false, error: "expired" }
→ rfxAuthGate() returns false → no auth, no trust
Attack D — Wrong Audience (token intended for another service) PASS — REJECTED
Attacker replays a legitimately signed token that was issued for a different service (wrong aud claim). The signature is valid but the audience doesn't match.
→ OS calls verifyToken(wrongAudToken)
→ System A /api/verify-token checks aud claim
→ Audience mismatch → { valid: false, error: "wrong-audience" }
→ rfxAuthGate() returns false → no auth, no trust
Attack E — Replay (reuse a single-use credential) PASS — REJECTED
Attacker captures a valid token and replays it. The jti (JWT ID) has already been consumed.
→ OS calls verifyToken(replayedToken)
→ System A /api/verify-token checks jti against consumed list
→ jti already consumed → { valid: false, error: "replay-detected" }
→ rfxAuthGate() returns false → no auth, no trust
Attack F — Stale Session (auth expired after initial login) PASS — HANDLED
Student authenticates successfully, then lets the auth token expire. The OS must follow the defined expiry/grace policy without silently converting expired identity into authenticated state.
→ Student authenticates → AUTH.authenticated = true, TRUST_VERIFIED = true
→ Time passes → AUTH.authExpiresAt is reached
→ OS session continues (grace period) but AUTH.authenticated stays true
→ On next page load: no valid token in URL → rfxAuthGate() returns false
→ loadHandshake() runs (dev fallback) → in production, no handoff → demo state
→ FUTURE: heartbeat validation will detect expired auth and transition to degraded state
Attack G — Identity Leakage (founder logout → another student login) PASS — BLOCKED
Founder logs out, then another student authenticates. No founder identity, founder flag, trust score, badge, or session time must carry over.
→ Founder clicks Logout
→ sesBank() deposits time → S.secs updated
→ clearOsSession("logout") → OS_SESSION ended, S._osSession.status = "ended"
→ AUTH state cleared: all fields reset to null/false
→ TRUST = null, TRUST_VERIFIED = false
→ S.handoff persists in localStorage (identity record, not trust)
→ Next student authenticates via token
→ rfxAuthGate() overwrites S.handoff with NEW verified claims
→ AUTH populated from NEW token (new studentId, new founder flag)
→ TRUST populated from NEW token trust data
→ TRUST_VERIFIED = true (from NEW authentication)
→ createOsSession() → NEW session ID, NEW studentId
→ NO founder identity, NO founder trust, NO founder badges carry over ✅
Attack H — Post-Auth URL Manipulation (modify URL after successful auth) PASS — BLOCKED
Student authenticates successfully, then modifies the URL (e.g., adds a different token, refreshes, or reopens the page). The OS must not reconstruct AUTH from anything client-controlled after the initial verification.
→ Student authenticates with valid token
→ rfxAuthGate() validates → AUTH populated → TRUST_VERIFIED = true → URL scrubbed
→ Student modifies URL to add ?token=attacker_token
→ Page reload → rfxAuthGate() captures new token → validates via /api/verify-token
→ If new token is invalid → production redirects to System A
→ If new token is valid for a DIFFERENT student → AUTH overwritten with new identity
→ AUTH is NEVER reconstructed from localStorage/S.handoff — only from fresh verification
→ Existing S.handoff is overwritten by verified claims, not restored from storage ✅
Attack I — Founder Logout → Direct /os/ Access PASS — BLOCKED
Founder authenticates, logs out, then accesses /os/ directly (no token in URL). Expected: clean unauthenticated state.
→ Founder authenticates → AUTH.authenticated = true, TRUST_VERIFIED = true
→ Founder clicks Logout → AUTH cleared, TRUST cleared, OS_SESSION ended
→ Founder navigates to /os/ (no token in URL)
→ rfxAuthGate() → no token → IS_DEV check
→ Production: redirects to System A (member.html)
→ AUTH.authenticated = false ✅
→ TRUST = null ✅
→ TRUST_VERIFIED = false ✅
→ OS_SESSION.status = idle ✅
→ S.handoff may exist in localStorage but is UNTRUSTED (TRUST_VERIFIED = false)
→ Ring shows: "— / Demo trader" ✅
Attack J — Student A → Manipulate localStorage to Student B PASS — BLOCKED
Student A authenticates. Attacker manipulates localStorage/S.handoff to show Student B's identity. AUTH must remain Student A.
→ Student A authenticates → AUTH.studentId = "RFX-00127", TRUST_VERIFIED = true
→ Attacker opens DevTools → modifies S.handoff.studentId to "RFX-99999"
→ AUTH.studentId remains "RFX-00127" (AUTH is a separate object, not derived from S.handoff)
→ AUTH.authenticated remains true (set by rfxAuthGate, not by S.handoff)
→ TRUST_VERIFIED remains true (set by rfxAuthGate, not by S.handoff)
→ standingCard() reads TRUST (from verified auth), not S.handoff.trust
→ The UI shows Student A's verified trust score, not the forged data ✅
→ NOTE: The visual manipulation may be visible in DevTools, but AUTH is the authority

Attack Summary

All 10 attacks are blocked or handled.

Attacks A–E: Rejected at /api/verify-token (System A side) — forged, fabricated, expired, wrong-audience, replayed tokens.
Attack F: Stale session — handled by OS session grace policy (auth expiry ≠ session destruction).
Attack G: Identity leakage — blocked by logout cleanup (AUTH + TRUST + OS_SESSION all cleared).
Attack H: Post-auth URL manipulation — AUTH is never reconstructed from localStorage, only from fresh verification.
Attack I: Founder logout → direct access — production redirects to System A, no unauthenticated state.
Attack J: localStorage manipulation — AUTH is a separate object, not derived from S.handoff. Visual manipulation doesn't affect authenticated state.
